# AI向けスライド生成アプリ 技術選定・設計決定事項

最終更新: 2026-09-24

## 目的

`sudonotfound/slide-generator`を参考に、AIがスライド作成時の前提・目的・判断を明示的に扱える、別リポジトリのスライド生成アプリを作成する。

## 基本方針

- AIがいきなりスライドを生成するのではなく、生成前に目的・対象者・利用場面・伝えたいことを整理する。
- AIは自動生成者ではなく、人間の思考を質問によって整理するアシスタントとして扱う。
- AIが推測した前提は、ユーザーが明示した情報と区別して管理する。
- 全体構成や各スライドの目的は、生成前に人間が確認できるようにする。
- AIと人間による編集対象は、Markdownではなく構造化データとする。

## AIの振る舞い

AIの生成手順はSkillとして定義する。

想定する流れ:

1. 資料の目的を確認する
2. 聴衆・利用場面・発表時間を確認する
3. AIが不足情報や推測した前提を整理する
4. 重要な未確認事項だけ質問する
5. 資料全体の構成案を作成する
6. 人間の確認を受ける
7. スライド単位の内容を作成する
8. 人間の確認を受けながら修正する
9. 出力形式に応じてレンダリングする

Skillは、質問手順・判断基準・フェーズ遷移を担当する。今回の資料固有の内容はJSONで管理する。

## 正本データ

正本はJSONとする。

1資料につき1つのJSONファイルを作成する。

```text
presentation.json
├── meta
├── context
├── assumptions
├── narrative
└── slides[]
```

`slides[]`に資料内の各スライドを格納する。

### JSON Schema

JSON Schemaによってデータ構造を検証する。

想定するスキーマ:

```text
presentation-context.schema.json
assumptions.schema.json
narrative-plan.schema.json
slide-document.schema.json
```

`slide-document.schema.json`は、スライドのデザインそのものではなく、資料全体と各スライドの構造・内容・意図を定義する。

デザインは以下で管理する。

```text
slide-document.schema.json = 内容・意図・構造
design-tokens.json        = 色・フォント・余白・サイズ
theme.css                 = 見た目のルール
renderer                  = JSONから各出力形式へ変換
```

## Markdownの扱い

Markdownを人間の編集対象にはしない。

Markdownは、Marp出力のためにアプリが自動生成する中間形式として扱う。

```text
presentation.json
  ↓
Marp用Markdownを自動生成
  ↓
Marp CLI
```

JSONとMarkdownの双方向同期は初期実装では行わない。

## レンダリング技術

### 初期採用: Marp

Marpを初期の出力エンジンとして採用する。

用途:

- PDF出力
- PPTX出力
- PNG出力
- 静的HTML出力
- テーマCSSの適用

Marpは編集環境ではなく、JSONから生成されたMarkdownを各形式へ変換する出力手段とする。

### 将来追加: Reveal.js

Reveal.jsは後から追加する。

用途:

- ブラウザ上のインタラクティブなプレゼンテーション
- アニメーション
- 段階表示
- スライド内の操作や状態変化

JSONにはReveal.js固有の属性や記法を直接持たせず、将来的に意味レベルの`motion`や`interaction`を追加する。

Marp出力ではアニメーション指定を静的なスライドとして扱い、Reveal.js出力ではアニメーションとして解釈する想定とする。

### 優先順位を下げる: 完全なHTML/CSS/JavaScriptレンダラー

JSONからHTML/CSS/JavaScriptを直接生成する方式は実装する可能性を残すが、初期優先度を下げる。

将来的には以下のようなレンダラー構成を想定する。

```text
presentation.json
  ├── Marp Renderer       ← 初期実装
  ├── Reveal.js Renderer  ← 将来追加
  └── HTML Renderer       ← 優先度低
```

AIには自由なHTML/CSS/JavaScriptを書かせず、JSONの意味構造を生成させ、レンダラー側の固定コンポーネントから出力する。

### 将来検討: PptxGenJS

PptxGenJSは、PowerPointを主要な出力先とする必要が出た場合に検討する。

初期段階では採用しない。Marp用コンポーネントとPptxGenJS用コンポーネントを二重管理する負担を避けるためである。

## 最新確定事項（2026-09-25）

### 利用形態

このリポジトリでは、以下の機能は実装対象外とする。

- ブラウザ上での人間による直接編集機能
- FigmaやPowerPointに代わる編集UI

生成したスライドは、HTMLとしてブラウザ上で閲覧できるようにする。
ただし、ブラウザ上での編集機能は実装しない。

人間が編集したい場合は、生成した資料をFigmaまたはPowerPointへエクスポートし、外部ツールで編集する。

資料は一度で完成させるのではなく、AIに都度指示を出しながら段階的に改善する。

```text
AIに指示
  ↓
JSONを更新
  ↓
資料を出力
  ↓
内容を確認
  ↓
再度AIに指示
```

### JSON形式

1資料1JSONファイルの形式を採用する。

JSONには、資料全体の情報と各スライドの内容・目的・使用コンポーネントを含める。

### コンポーネント

AIが新しいコンポーネントを追加できる設計を目指す。

コンポーネントの詳細な契約・構造・追加手順は、今後別途議論する。

デザインの再利用性は、単純な使用回数だけでは判断しない。以下の観点で扱う。

- 今後も似た用途で使えるか
- 内容とレイアウトを分離できるか
- パラメータ化できるか
- 共通部品として維持する価値があるか

デザインの管理レベルは次の3段階とする。

```text
資料専用デザイン
  ↓
資料内テンプレート
  ↓
共通デザインシステム
```

- 資料専用デザイン: 今回の資料でしか使わない特殊なレイアウト
- 資料内テンプレート: 同じ資料内で複数回使うレイアウト
- 共通デザインテンプレート: 複数の資料で再利用できるレイアウト

AIは、既存コンポーネントで表現できない場合に新規デザインを提案する。新規デザインは、最初から共通部品として登録せず、資料専用または資料内テンプレートとして作成し、再利用価値が確認できた場合に共通デザインシステムへ昇格する。

共通テンプレートへの登録・昇格は、AIが無断で行わず、人間に確認する。

### Skill

AIへの質問フローや資料生成手順はSkillとして定義する。

ただし、質問項目・質問順序・フェーズ定義の詳細は今後決定する。

Skillは以下の役割に分ける想定とする。

```text
slide-authoring
  = 既存デザインを使って資料を作成する

design-system-extension
  = 新しいデザインコンポーネントを追加・昇格する
```

### 検証

以下の検証を行う。

- JSON Schemaによる構造検証
- 各スライドの目的・メッセージの有無を確認する内容検証
- 出力後の文字切れ・レイアウト崩れを確認する表示検証

### エクスポートに関する注意

FigmaやPowerPointで人間が編集することを想定するが、PowerPoint出力の優先順位は高くないため、初期実装の対象外とする。

初期実装では、HTMLブラウザ閲覧とMarpによるPDF・画像出力を優先する。
PowerPoint出力や編集可能なFigma／PowerPointオブジェクトへの変換は、将来の検討事項とする。

Marpやopen-slideのPPTX出力は、実装方法によってはスライド全体が画像として配置される可能性があるため、テキスト・図形・画像を個別に編集できるPPTXが必要かを確認する。
